## Summary (read this first)

6. **Comparable apps**: Letterboxd (film-only, social-heavy, biggest player), Trakt (auto-scrobble + stats, weaker social), Serializd (TV-focused social), TV Time — **already discontinued July 15, 2026** [8][9][10], a cautionary tale on ad creep, not a live competitor.
7. **Top complaints across the category**: intrusive/rising ads on free tiers, no unified movie+TV tracking, weak recommendations, poor cross-platform performance. Perchable's gap: free-first, tight movie+DM+ranking combo nobody nails at once.
8. **Swipe-to-add**: `react-native-gesture-handler` + `react-native-reanimated` directly, the 2026 professional pattern, rather than a wrapper lib [11].

## 1. Movie data source — IMDb vs TMDB vs OMDb

**IMDb.** The official Conditions of Use say: "You may not use data mining, robots, screen scraping, or similar data gathering and extraction tools on this site, except with our express written consent" and that IMDb content "may not be reproduced, duplicated, copied, sold, resold, ... or otherwise exploited for any commercial purpose without express written consent of IMDb" [1]. IMDb does sell a structured commercial data feed via AWS Data Exchange, and offers free plain-text data dumps for personal/non-commercial use only [1]. Justin's Vision Part 1 literally asks "(scrapped by n8n in imdb... [is that correct?])" — **the answer is no**, not for an app headed to the Play Store and portfolio, even before monetizing.

**TMDB (The Movie Database).** Official API Terms of Use: free for non-commercial use as long as you attribute TMDB (their logo, less prominent than the app's own branding, plus the exact notice: "This app uses TMDB and the TMDB APIs but is not endorsed, certified, or otherwise approved by TMDB") [2]. Any monetized use — charging users, ads, or using the data to power recommendations sold commercially — requires a separate written commercial agreement with TMDB [2]. No published daily request cap; per-second ceiling is roughly 40-50 requests/sec per IP via their CDN, with 20 connections per IP [3]. Data cannot be cached for longer than 6 months without re-syncing, and TMDB may not be used purely as an image CDN or fed into chatbots/LLMs without a commercial deal [2].

**Does a free, no-ads Play Store app count as "commercial" under TMDB's terms?** TMDB's own FAQ defines it plainly: "Your project is considered commercial if the primary purpose is to create revenue for the benefit of the owner" [2]. Perchable as planned for v1 (free, no ads, no in-app purchases, per Vision Part 4) generates no revenue, so **it qualifies as non-commercial and the free API key with attribution is sufficient for launch** — no license needed to ship to the Play Store as-is, and being listed on a commercial storefront (Google Play) does not by itself trigger the requirement; the test is revenue intent, not distribution channel [2]. The moment ads (or any paid tier/IAP) are added, per Vision Part 4's "in the future, we will have ads," the app crosses into commercial use and Justin needs to **contact TMDB's sales team at sales@themoviedb.org before turning ads on**, not after [2]. **UNVERIFIED nuance**: TMDB's terms and FAQ address monetizing *the app as a whole*; I found no page that separately carves out "ads unrelated to movie content" — treat any ad revenue as triggering the commercial requirement unless TMDB says otherwise when contacted.

**OMDb.** Donation/Patreon-funded, paid tiers (from ~$1/mo) raise the request cap and unlock the Poster API [15]. **UNVERIFIED — "1,000 requests/day free"**: I fetched omdbapi.com directly this round and its page does not state a specific free-tier daily limit; the 1,000/day figure only appears in secondary blog summaries, not the primary source, so it is not stated as fact here [15]. Thinner dataset than TMDB, same underlying IMDb-licensing lineage, less well documented than TMDB's own terms.

**Recommendation:** TMDB API, called from your own backend (not directly from the client, so the API key stays server-side and you control caching/attribution centrally). Store only what a user actually interacts with (their collection, cached search/browse results with a TTL under 6 months) rather than mirroring the entire catalog. This directly answers Justin's "n8n scrapes IMDb -> Cloudflare DB" question: drop the scrape, keep the "backend DB" idea but populate it from TMDB via API calls (either live pass-through, or a lightweight cache table you populate on demand).

**Answering Justin's literal question — should we use Cloudflare for the database?** Not recommended as the primary backend for Perchable. Cloudflare D1 is a solid SQL database, but it ships with no built-in authentication and no built-in realtime layer — both of which this app needs on day one (Google sign-in, DMs). You'd be assembling Workers + D1 + Durable Objects (for the DM websocket layer) + a hand-rolled OAuth/PKCE flow yourself [16][17]. That's a legitimate learning exercise, but it roughly triples the backend surface area of a "test base build," which cuts against Vision Part 0's modular/learning goal by making the base harder to reuse and debug. Supabase gives you Postgres + Auth + Realtime + Storage as one coherent, documented product with an official Expo guide [7], for the same "learn proper backend concepts" value (SQL, RLS policies, row-level auth) without hand-building the plumbing.

**Risk: Supabase free-tier idle pause.** Free-tier Supabase projects pause automatically after 7 days with no API activity [4]. A dev/demo app sitting untouched for a week (e.g., between Builds, or after a milestone with no active users yet) will go to sleep and need a manual un-pause in the dashboard before it responds again. This is a real risk for "done means all functions working in local emu (not shipped yet)" (Vision Part 5) if there's a testing gap longer than a week, and a bigger risk once it's a live Play Store app with real but sparse users — a paused DB means the app is down for whoever opens it next. Mitigation: either accept manual un-pausing during Stage B (cheap, just needs the Manager to notice), or move to the $25/mo Pro plan before Play Store launch, which removes the pause [4]. Flag this as a decision point for Justin closer to launch, not now.

**Recommended end-to-end flow (one paragraph):** App (Expo/React Native, Google sign-in via Expo dev build + `expo-auth-session` against Supabase Auth) → Supabase Postgres holds users, follows, collections, captions, comments, DMs (via Supabase Realtime channels), rankings (materialized views or scheduled aggregation) → a thin server function (Supabase Edge Function or a small Worker) proxies TMDB API calls, attaches the required attribution, and optionally caches responses in a `movies_cache` table inside the same Postgres DB → app never talks to TMDB directly, so the API key stays server-side.

As of today (2026-09-24) it is no longer a live competitor — its value here is as a cautionary example of what drove users away (ad creep, feature paywalling), not a benchmark to match feature-for-feature.

## 4. UX patterns and library choices

- **Swipe-to-add ("Quick add," Vision Part 2).** Use `react-native-gesture-handler` + `react-native-reanimated` directly rather than a pre-built wrapper like `react-native-deck-swiper`: it's the pattern described as the current professional standard (silky 60fps, full control over gesture thresholds/sequence ordering), and since Vision Part 0 frames this whole build as a learning exercise, building the gesture logic by hand is the more valuable lesson than a drop-in library [11].
- **Discord-style profile popup modal (Vision Part 2, `docs/inspo/discord_modal.png`).** Two real options: `@gorhom/bottom-sheet` (Reanimated + Gesture Handler under the hood, real snap points, backdrop, keyboard avoidance, scrollable content via `BottomSheetFlatList`) versus Expo Router's native `formSheet` modal presentation (less code, genuine platform-native sheet, but iOS-only presentation behavior — Android renders it as a plain screen, and it has no half-open/snap-point states) [18]. Since the Discord modal look is a fixed-height popover (profile info, stats, follow button) rather than something that needs to peek/expand, **Expo Router's `formSheet`/modal route is the leaner choice on Android** where it behaves as a full screen anyway; reach for `@gorhom/bottom-sheet` only if Justin later wants a half-open "peek" state (e.g., a draggable profile preview over the home feed) [18].
- **Comments threading + notifications.** No dedicated RN library needed — this is a data-modeling problem, not a UI-library problem. Store comments as a self-referencing table (`parent_comment_id`) in Supabase Postgres, and drive notifications off Supabase Realtime's Postgres-change subscriptions (insert on `comments`/`dms` tables triggers a client-side toast/badge for the recipient) [5]. Serializd's "Incoming" page — a dedicated feed of replies/likes on your content — is the pattern to copy structurally [9], since it was called out as a genuine social-UX strength versus Letterboxd's flatter comment model [8].
- **DMs.** Supabase Realtime channels (the same primitive as comments/notifications above) — a `dms` table with `sender_id`/`recipient_id`/`conversation_id`, RLS restricting rows to the two participants, and a Realtime subscription per open conversation [5]. No separate chat SDK needed at this scale.
- **Comment on/off toggle (Vision Part 2: "profile owners can set whether to enable or disable commenting").** This is a single boolean column (e.g., `profiles.comments_enabled`) enforced two places: (1) a Postgres RLS policy on the `comments` table's INSERT rule — `EXISTS (SELECT 1 FROM profiles WHERE id = movie_owner_id AND comments_enabled = true)` — so it's enforced at the database layer, not just hidden in the UI, and (2) the client hides the comment composer when the flag is off. This also interacts with the Play Store UGC/moderation requirement below: disabling comments is a legitimate user-level moderation control, but it does **not** substitute for the required report/block system on DMs and on any comments made before the toggle was switched off — see section 6.
- **Rankings (Vision Part 2: "most added," "most discussed," "most watched," "most active").** Keep an append-only events/activity table as the source of truth (one row per watch/comment/follow action), and compute the leaderboard aggregates as **Postgres views first**, only promoting a view to a **materialized view + `pg_cron` scheduled refresh** once a plain view's query shows up as a genuine slow-query bottleneck — premature materialization just adds a staleness bug for no benefit at this app's scale [19]. `pg_cron` is the standard Supabase-recommended way to schedule that periodic refresh (e.g., every 15–60 minutes) directly inside Postgres, no external cron service needed [19]. Cost: `pg_cron` and materialized views are plain Postgres features included in Supabase's free tier — no extra charge, only the DB compute you're already paying for [19].

## 5. Proper mobile tech stack (what "proper mobile development" looks like)

- **Server/remote state.** TanStack Query (formerly React Query) over the Supabase client — it's the current default for apps with real mutation complexity (add-to-collection, follow/unfollow, comment CRUD), with 12.3M weekly downloads versus SWR's 7.7M and explicit strength in "complex mutations, infinite scroll, cache seeding" — exactly Perchable's shape (paginated browse, optimistic swipe-add) [20]. Keep a separate, small local-state layer (React's own `useState`/context, or Zustand only if genuinely global UI state like "current swipe deck order" accumulates) — don't force one library to do both jobs [20].
- **Poster image caching.** `expo-image`, not `react-native-fast-image` — fast-image's development has slowed and it doesn't support React Native's New Architecture as of mid-2026, while `expo-image` is the maintained, Expo-native solution with proper disk/memory caching, placeholders, and transitions, and pairs directly with FlashList for smooth poster-grid scrolling [21].
- **Lists.** FlashList (Shopify) — already recommended in section 9, repeated here as the "proper stack" answer for large scrolling movie/collection grids versus core `FlatList`'s frame drops on big datasets [not re-cited, see source 22 below in original list].
- **Testing.** Jest + React Native Testing Library for unit/component tests (the Expo-documented default, `jest-expo` preset handles Expo config automatically) [23], plus Maestro for E2E flows (YAML-based, no native build config changes, fastest setup of the E2E options evaluated) [23] — e.g., one Maestro flow for "sign in with Google → swipe to add a movie → see it in collection" as the single smoke test that proves the whole stack works end to end.
- **Error/crash reporting.** Sentry's React Native SDK, which works with Expo/EAS out of the box and links crash reports/session replays directly from the EAS dashboard [24] — worth wiring in before the Play Store closed-testing phase (section 6) so Justin can see what the 12 testers actually hit.

## 6. Play Store: UGC moderation and account deletion (both required before production access)

Perchable has comments, DMs, and public profiles — this puts it squarely inside Google Play's User Generated Content policy, not an edge case. Two separate requirements, both checked at review:

**UGC report + block [13].**
- Every piece of user-generated content — comments, DMs, profile info — must have an accessible in-app "report" path. Google's guidance is explicit that reporting should be reachable from every UGC surface, not bolted on to just one screen.
- One-on-one features (DMs, and by extension the follow/profile-visit model) specifically require **in-app user blocking**, separate from content reporting.
- The app must require users to accept terms of use / a user policy before they can post UGC (comment, DM, set a profile caption), and those terms must define what counts as objectionable content.
- Google reviewers check that moderation is *active*, not just present: the app must "take action against UGC or users where appropriate" — a report button that goes nowhere fails review. At minimum this means someone (Justin, initially) reviewing reports and being able to remove content/ban a user account from the backend (a Supabase admin query is enough at this scale; no dedicated admin panel needed for v1).
- **How this maps onto Supabase/RLS**: a `reports` table (reporter_id, target_type [comment/dm/profile], target_id, reason, created_at) with RLS so users can insert their own reports but only a service-role/admin can read across all reports; a `blocked_users` table (blocker_id, blocked_id) that gets checked in every comments/DMs RLS policy (`WHERE NOT EXISTS (SELECT 1 FROM blocked_users WHERE blocker_id = recipient AND blocked_id = sender)`) so a block is enforced at the database layer, not just hidden in the UI.
- This is Priya-relevant: report + block needs to be a Build item in its own right, not a stretch goal — the app cannot go past closed testing into production without it, per the policy page [13].

**Account deletion [14].**
- Because the app has account creation (Google sign-in), Google requires **both**: an in-app path to delete the account and its data (commonly a button in account settings), **and** a web page/URL where a user can request the same deletion without having the app installed.
- Deletion must cover all data disclosed in the Play Console "Data safety" form for the account — profile info, collection/watch history, comments, DMs, follow graph. Justin can retain data only for narrowly legitimate reasons (fraud prevention, legal compliance) and must disclose that retention.
- Practically: a `DELETE FROM profiles WHERE id = ...` with `ON DELETE CASCADE` set up correctly across the schema (follows, comments, DMs, collection rows) handles the in-app side in Postgres; the web-URL requirement needs a simple static page (could live on justin94.space or a Supabase Edge Function form) that accepts a deletion request by email/account ID for someone who deleted the app before deleting their account.
- Like report/block, this blocks production access — build it alongside auth, not as a late add-on.

## 9. Gaps — where Perchable can stand out
